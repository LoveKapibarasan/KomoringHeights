# 設計原則

このプロジェクトは、詰将棋の**生成・探索**という本質的にランダム性を含む領域で、いくつかの明確な原則を採用しています。

## 1. 禁止禁止の原則

`CLAUDE.md` に明文化されている、生成・探索系コードの基本方針です。

> 生成・探索系のコードでは「禁止（skip/continue で候補を完全排除）」を避け、**確率を下げる**方向で実装する。

### NG / OK の対比

```cpp
// NG: ハードな禁止（分布がいびつになる）
if (bad_condition) continue;

// OK: 確率を下げる（20% で採用）
if (bad_condition && rng() % 5 != 0) continue;
```

### なぜか

ハードな禁止は**分布を歪め、想定外の偏り**を生みます。人間の判断が「絶対にダメ」ではなく「原則としてダメ、例外もあり」であるように、**確率を下げる**ことで自然な探索分布を維持します。

### 適用例

| 状況 | 実装 |
|---|---|
| 追い詰め候補（攻方に打ち手ゼロ） | 禁止ではなく 20% の確率で採用 (`user-search.cpp:2651`) |
| 変同ありの近傍 | 禁止ではなく摂動で確率を下げて再試行 |
| 重複局面 | **完全スキップは OK**（実際に無意味な重複なので） |

**例外**: 意味的に無意味な重複（同じ局面の再登録など）は普通に `continue` してよい。この原則は「意味のある選択肢を確率で扱う」ためのものです。

## 2. 39枚制は絶対要件

詰将棋の**完全性**を担保するための絶対規則です。

- 盤上 + 双方持駒 = **39枚**（片玉）または **40枚**（双玉）
- スパース SFEN（駒不足）を最終解として保存することは禁止
- **駒余りも禁止**（詰め上がりで攻方の余剰駒 = 不完全作）

実装上は `CompleteDefenderReserve` (`tsume_generator.hpp:437-484`) が、生成された不完全 SFEN に対して**受方持駒を自動補完**し、39/40枚制を復元します。

## 3. 逆算式（Retrograde）を基本とする

過去、正算式（初期局面から前向きにランダム展開）で 9手詰め生成を試みて**失敗**しました。理由:

- **収束しない**: 攻方の初手候補が多すぎ、目標手数まで詰まないケースが大半
- **分布が悪い**: 生成できた問題も「王手放置しないための追い詰め」ばかりに

現在は **詰め上がり局面から逆算**して条件を満たす形を作ります。詳細は [生成アルゴリズム](flow.md) を参照。

## 4. 完全性は探索で保証する

「これは詰将棋作品だ」と主張するには、以下を全探索で確認する必要があります。

1. **作意成立**: 攻方最善で必ず詰む
2. **作意唯一**: 攻方の任意手順に別解がない
3. **駒余りなし**
4. **無駄合排除**: 中合が即取りされる場合は除外

ヒューリスティックなショートカット（例: 最初に見つけた作意で判断）は使わず、**AND/OR 全探索**（`ExhaustiveVerifier`）で確認します。

## 5. 美的評価は複合指標で

美しさは単一の指標では表せないため、**11 次元のスコア** + **廣瀬 1998 の X 変数**の組み合わせで評価します。

- 完全性ゲート（`aestheticPass`）と美的ゲート（`aestheticScore ≥ 35`）の**二段構え**
- 追い詰め判定は特別扱い（`chaseRatio` ≥ 0.75 でペナルティ）

詳細は [検証と美的評価](verification.md) を参照。

## 6. 出力は SFEN + JSONL の 2 系統

- `.sfen`: 問題集として使える一行 SFEN 形式
- `.sfen.jsonl`: 検証結果・美的スコア・技巧統計・X 変数を含む完全記録

JSONL 側は 1 レコード / 1 行で、機械学習や統計解析に流し込む前提の設計。詳細は [JSON 出力仕様](json-format.md) を参照。
